## 2. Exploración del esquema de Chyrp Lite (Parte 2)

* **¿Qué tablas hay y para qué sirve cada una?**
  * `posts`: Registra la cabecera/metadatos de cada entrada (id, fecha, slug, estado, usuario).
  * `post_attributes`: Almacén EAV (Entity-Attribute-Value) donde se guardan el título, el cuerpo y las etiquetas.
  * `pages`: Almacena páginas estáticas independientes del feed del blog.
  * `users`: Cuentas de usuarios y administradores.
  * `groups` y `permissions`: Control de acceso y roles.
  * `sessions`: Sesiones activas de usuarios.
* **¿Cuántas filas ocupa cada entrada en cada tabla?**
  * Ocupa **1 fila** en `posts` y **3 filas** en `post_attributes` (`title`, `body` y `tags`). El título y el cuerpo se guardan como atributos en `post_attributes`.
* **Clave primaria de post_attributes:**
  * Compuesta por `(post_id, name)`. Debe ser compuesta porque una entrada puede tener varios atributos distintos pero nunca dos con el mismo nombre. Clave foránea: `post_id` referenciando a `posts(id)`.
* **¿Existe tabla de etiquetas?**
  * No existe. Las etiquetas se almacenan como JSON dentro de `post_attributes` bajo `name = 'tags'`. Si tiene etiquetas guarda `{"etiqueta":"slug"}`; si no tiene guarda `[]`.
* **Fechas y valores centinela:**
  * Formato `YYYY-MM-DD HH:MM:SS`. En entradas no editadas, `updated_at` almacena el valor centinela `'1000-01-01 00:00:00'`.
* **clean vs url:**
  * `clean` es el slug normalizado; `url` es la ruta canónica del post. `status` toma valores como `public`, `draft`, `private` o `registered_only`.
* **Modelo EAV:**
  * Permite añadir atributos arbitrarios mediante módulos sin modificar el esquema físico de la base de datos (sin `ALTER TABLE`), a costa de requerir múltiples `JOIN` para reconstruir una entrada y perder comprobaciones de tipo SQL nativas.

## 3. Tabla de correspondencia entre esquemas (Parte 3)

| Prototipo (P1.1) | → | Chyrp Lite (tabla.columna o atributo) | Transformación necesaria |
| :--- | :---: | :--- | :--- |
| **título (title)** | → | `post_attributes (name='title')` | Directo |
| **cuerpo (.md)** | → | `post_attributes (name='body')` | Copiado íntegro conservando formato Markdown |
| **fecha (date)** | → | `posts.created_at` | Conversión a formato `YYYY-MM-DD HH:MM:SS` |
| **nombre fichero** | → | `posts.clean` y `posts.url` | Conversión a slug con `slugify()` |
| **description / summary**| → | *(Sin equivalente directo)* | Se omite para no redundar |
| **etiquetas (tags)** | → | `post_attributes (name='tags')` | Serialización de lista a JSON `{"tag":"slug"}` |
| **draft: true** | → | `posts.status` | `'draft'` si es borrador, `'public'` si no |
| **autor** | → | `posts.user_id` | Se asigna el ID del usuario administrador |
| **columnas fijas** | → | `posts.feather`, `pinned`, `updated_at` | `feather='text'`, `pinned=0`, `updated_at='1000-01-01 00:00:00'` |

## 4. Respuestas a la lectura guiada del script (Parte 4.4)

1. **Funciones puras vs con efectos:**
   * `slugify`, `fecha_chyrp`, `etiquetas_json`, `transformar` y `transformar_pagina` son **puras** (mismos argumentos = mismo retorno, sin I/O ni estado global).
   * `extraer` y `cargar` son **impuras** (leen de disco y escriben en SQLite).
   * `test_migrar.py` puede probar las puras sin necesidad de levantar bases de datos ni crear ficheros temporales.
2. **Límites de la transacción:**
   * Empieza en `with con:` dentro de `cargar()` y termina al salir del bloque. Si la 3ª entrada falla, el bloque ejecuta un `ROLLBACK` y revoca todas las inserciones previas, dejando la base de datos intacta.
3. **Control de duplicados:**
   * Utiliza la columna `url`. Es adecuada siempre que los slugs sean únicos. Si hubiera dos ficheros con el mismo nombre en distintas carpetas, el segundo se omitiría.
4. **Serialización de etiquetas:**
   * Chyrp Lite almacena `[]` cuando no hay etiquetas y un diccionario `{nombre: slug}` cuando sí las hay.
5. **Fecha centinela:**
   * `1000-01-01 00:00:00` es el estándar que utiliza Chyrp Lite para indicar que una entrada es original y nunca ha sido editada.
6. **cur.lastrowid:**
   * Recupera el identificador autoincremental recién creado en `posts` para enlazar inmediatamente sus atributos correspondientes en `post_attributes`.

## 6. Ejercicios resueltos (Parte 7)

### Ejercicio 1: Rompe la transacción a propósito
* **Cambio:** Se añadió `--romper-transaccion 3` para provocar un `RuntimeError` en la 3ª inserción.
* **Comprobación con transacción (`with con:`):** Tras el fallo, `SELECT COUNT(*) FROM posts` arrojó **2 filas** (las originales). Ninguna entrada incompleta fue confirmada (Atomicidad).
* **Comprobación sin transacción (`--sin-transaccion`):** Tras el fallo, la base de datos contenía **4 filas**, dejando el catálogo en un estado corrupto y a medias.

## 7. Mini-reto y Preguntas de reflexión

### Mini-reto:
* Se publicó una nueva entrada con etiquetas `sql` y `sgbd`.
* En la base de datos se generó **1 fila en `posts`** (id 8) y **3 filas en `post_attributes`** (`title`, `body` y `tags`).
* La consulta de entradas por etiqueta requiere buscar texto serializado mediante `LIKE '%:"sql"%'` sobre `post_attributes`, lo cual es ineficiente en comparación con el `JOIN` relacional sobre la tabla normalizada `tags` de Hugo.

### Preguntas de reflexión:
1. **Disponibilidad:** En el prototipo estático (Hugo), la caída de SQLite solo impacta al tiempo de build; la web servida en Nginx/Apache sigue online. En Chyrp Lite, cada petición HTTP consulta la base de datos; si SQLite se bloquea o cae, el sitio entero queda fuera de servicio.
2. **Concurrencia:** SQLite bloquea el fichero entero al escribir. Si múltiples usuarios editan o comentan a la vez, se provocan bloqueos (`database is locked`). Para alta concurrencia es necesario migrar a motores cliente-servidor como PostgreSQL o MariaDB.
3. **Copias de seguridad:** En Chyrp Lite la base de datos es la única fuente de la verdad (si se pierde el `.sqlite`, se pierde el contenido). En Hugo la fuente de la verdad son los ficheros `.md` versionados en Git, y la base de datos es un artefacto desechable.
4. **Normalización vs Flexibilidad:** Guardar las etiquetas como JSON asociativo viola la 1ª Forma Normal y dificulta la indexación relacional, pero le permite a Chyrp Lite admitir módulos de terceros sin modificar la estructura de las tablas existentes.
